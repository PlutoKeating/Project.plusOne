# 全站类比对照表（唯一标准）

全站所有"打个比方"、类比、动画里的比喻，都只用 **「加一餐厅」** 这一个场景。每个概念固定对应一个类比物，所有页面、卡片、术语悬浮卡（`docs/assets/terms.json`）、动画（`animations/src/scenes/`）必须一致。

新增概念时先在本表登记，再写进文档。

## 1. 角色分工（最重要，任何页面都不能换位）

| 原概念 | 类比物 | 说明 |
|--------|--------|------|
| 加一（整个 AI 应用 / Agent） | **加一餐厅** | 整家店 |
| 用户 | **顾客** | 提需求、吃结果的人 |
| LLM（大语言模型） | **主厨** | 只在后厨动脑：看单子、想做法、决定要什么食材。不出门、不碰收银、不自己跑腿 |
| 你的程序（开发者写的代码） | **服务员 / 帮厨** | 传话、跑腿、按主厨的领料单去取东西、把结果端回去 |
| 开发者（你） | **餐厅老板** | 定规矩、招人、买设备 |

固定关系：**顾客点单 → 服务员把订单递进后厨 → 主厨决定做法 → 需要东西时主厨开领料单 → 帮厨去取 → 主厨做完 → 服务员端给顾客。**

禁止出现：把 LLM 比作顾客/点菜的人；把程序比作主厨；把用户比作厨师。

## 2. 第 1 章 Python 基础

| 原概念 | 类比物 |
|--------|--------|
| 变量 | 贴了标签的调料罐 |
| 字符串 | 小票上写的一行字 |
| 列表 list | 订单夹：按先后顺序夹着的一沓订单 |
| 字典 dict | 菜单：菜名 → 价格 |
| 函数 | 标准作业卡：照着做就出一道菜，随时可以再用 |
| 循环 | 一张一张处理订单夹里的单子 |
| 条件判断 | 看订单上写"要辣"还是"不要辣"，分开做 |
| 异常处理 try/except | 后厨应急预案：一个灶出状况，换灶继续，整个厨房不停摆 |
| JSON | 统一格式的订单小票 |
| HTTP 请求 / 请求库 | 服务员打电话给供应商 |
| 文件读写 | 从档案柜取单据、往档案柜存单据 |
| 虚拟环境 | 每家分店一套独立厨具，互不借用 |

## 3. 第 2 章 LLM API

| 原概念 | 类比物 |
|--------|--------|
| API | 后厨的传菜窗口：订单从这里递进去，菜从这里递出来 |
| API Key | 餐厅给老板的记账卡号：凭它下单，按它扣费，丢了别人就能刷你的账 |
| Base URL | 后厨（服务商）的地址 |
| SDK | 点单机：帮你把订单按格式填好送进窗口 |
| `.env` 文件 | 老板抽屉里上锁的小本子，放记账卡号 |
| model（选模型） | 选哪位主厨 |
| messages 消息列表 | 这一桌从头到尾的订单记录 |
| System Prompt / system 角色 | 老板贴在后厨墙上的规矩：本店风格、忌讳 |
| user 角色 | 顾客说的话 |
| assistant 角色 | 主厨之前出过的菜 |
| temperature | 主厨的发挥空间：0 照菜谱一丝不差，调高就即兴创作 |
| max_tokens | 一道菜的分量上限 |
| Token | 计价单位：按"字块"称重计费 |
| 多轮对话 | 主厨记不住这桌点过什么，服务员每次把整本订单记录一起递进去 |
| 幻觉 | 主厨没翻菜谱，凭印象报出一道店里根本没有的菜 |
| Prompt（提示词） | 递给主厨的订单：写清楚要什么 |

## 4. 第 2 章附加阅读 Self-Attention

| 原概念 | 类比物 |
|--------|--------|
| Self-Attention | 主厨读一张订单时，每个词都去看其他词，弄清自己的意思（"不要辣"里的"不要"盯着"辣"） |
| Query (Q) | 每个词举的牌子："我在找什么" |
| Key (K) | 每个词举的牌子："我是什么" |
| Value (V) | 每个词真正携带的内容 |
| 注意力权重 | 看别的词时花了几成注意力 |
| Transformer | 主厨的大脑结构 |
| RNN | 主厨从头到尾一个字一个字读订单，读到后面忘了前面 |

## 5. 第 3 章 RAG

| 原概念 | 类比物 |
|--------|--------|
| RAG | 主厨先翻菜谱库再做菜，不凭记忆瞎做 |
| 知识库 / 原始文档 | 餐厅的菜谱库 |
| 切块 Chunking | 把厚菜谱拆成一张张菜谱卡 |
| Embedding | 给每张菜谱卡标上"口味坐标"，味道相近的坐标也相近 |
| 向量 | 这串口味坐标 |
| 向量库 | 按口味坐标摆放的菜谱柜，找相似的卡很快 |
| 检索 / Top-K | 按顾客需求的口味坐标，从柜里取最接近的 K 张卡 |
| Prompt 组装 | 把选出的菜谱卡和订单夹在一起递给主厨 |
| 建索引流水线 | 开业前把菜谱拆卡、标坐标、上柜 |
| 查询流水线 | 每来一单：算口味坐标 → 取卡 → 递给主厨 → 出菜 |
| Lost in the Middle | 夹的卡太多，主厨只认真看了最上面和最下面几张 |

## 6. 第 4 章 Agent

| 原概念 | 类比物 |
|--------|--------|
| Agent | 能自己安排整套做菜流程的后厨（主厨 + 帮厨 + 设备） |
| Chatbot（只会对话） | 只会口头报菜名、不能下厨的主厨 |
| Tool 工具 | 厨房设备和外部供应商：烤箱、秤、菜市场 |
| 工具清单 / 工具描述 | 墙上的设备说明牌：叫什么、能干什么、要放什么 |
| Function Calling | 主厨开领料单（要什么、多少），帮厨照单去取，取回交给主厨 |
| ReAct 循环 | 做一步、尝一口、再决定下一步 |
| 对话记录 | 这道菜的操作记录本：每一步做了什么、结果如何 |
| 最多步数 | 一道菜最多返工 N 次，超了就向顾客说明 |
| 工具报错交回 LLM | 仓库没货也要回话"没货"，主厨换食材，后厨不停摆 |

## 7. 第 5 章 Tool / MCP / Memory

| 原概念 | 类比物 |
|--------|--------|
| MCP | 统一的供货标准：所有供应商按同一种送货单格式接入，后厨不用为每家改流程 |
| MCP Host | 餐厅本身 |
| MCP Client | 餐厅里专门对接某一家供应商的采购员 |
| MCP Server | 供应商 |
| 上下文窗口 / 短期记忆 | 出餐台上的订单夹：只能夹有限几张，新单进来旧单被挤掉 |
| 长期记忆 | 老顾客档案本：爱吃辣、忌口、上次点了什么 |
| 记忆检索 | 按口味坐标翻档案本，只取和这次相关的几条 |

## 8. 第 6 章 Multi-Agent

| 原概念 | 类比物 |
|--------|--------|
| Multi-Agent | 后厨团队分档口协作 |
| Orchestrator 协调者 | 行政总厨：拆单、派活、最后把关 |
| Worker Agent | 各档口厨师：冷菜、热菜、甜点 |
| 独立上下文 | 每个档口只看自己那张单 |
| 串行流水线 | 一道菜按工序往下传：切配 → 炒 → 装盘 |
| 并行分派 | 几个档口同时做不同的菜 |
| 评审 / 质检 Agent | 出菜前的试菜员 |

## 9. 附录 Prompt 工程

| 原概念 | 类比物 |
|--------|--------|
| Prompt 五要素 | 订单的五栏：角色（找哪种风格的主厨）、任务（做什么菜）、背景（几位客人、忌口）、输出（要端出什么）、格式（怎么装盘） |
| 思维链 Chain of Thought | 让主厨先把做法步骤说一遍再动手 |
| Few-shot 示例 | 先给主厨看两道样菜 |

## 写作规则

1. 同一概念在全站只用表中的类比物，措辞可以变，角色不能变。
2. 一个类比只讲一个关系，不要在同一张卡里混两个场景。
3. 表中没有的概念，优先在"加一餐厅"里找类比，并登记到本表。
4. 章节叙事里"加一的身体 / 眼睛 / 双手"是成长故事的称呼，可以保留；正文和卡片里的"打个比方"一律用餐厅场景。
5. 不再使用的旧类比：图书馆、USB-C、快递、便利贴、通讯录、点外卖、修自行车、走钢丝等；遇到就换成本表对应项。
